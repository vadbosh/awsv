# awsv — подробности

Краткое руководство — [README.RU.md](../README.RU.md). Здесь — как awsv устроен и
что легко упустить.

## Как это работает

`~/.aws/config` велит AWS CLI не читать ключ из файла, а спрашивать его у awsv.
Так устроен каждый вызов `aws`, каждый прогон Terraform и каждое обращение SDK:

```
aws s3 ls
  │  ~/.aws/config: «ключ взять у: awsv creds work»
  ▼
awsv
  │  открывает keys/work.gpg — для этого нужен пароль work,
  │  его держит в памяти gpg-agent столько, сколько вы выбрали
  │
  ├─ режим session: меняет ключ на часовую сессию в AWS STS
  └─ режим direct:  отдаёт сам ключ
  ▼
aws подписывает запрос тем, что вернул awsv
```

Отсюда три следствия:

- **Ключ на диске зашифрован.** Без пароля файл — нечитаемый набор байтов.
- **`~/.aws/credentials` остаётся пустым.** Так и должно быть, это не поломка.
- **Если аккаунт заперт и пароль ввести некому, вызов падает.** У задания cron,
  скрипта или ИИ-ассистента нет терминала, где можно спросить пароль. Доступ
  закрывается сам, а не остаётся открытым, и закэшированная сессия — вместе
  с ним.

## Что сейф не защищает

Пока аккаунт открыт, никто не спрашивает разрешения прочитать его ключ. Любой
процесс под вашим пользователем получит ключ через `gpg --decrypt` — без пароля
и без вопроса. Это касается скриптов, заданий cron и ИИ-ассистента, запущенного
под вами. Ровно благодаря этому `aws` и Terraform работают, не спрашивая пароль.
Подтверждения на каждое использование такого ключа у gpg-agent нет.

| Сейф защищает | Сейф не защищает |
|---|---|
| ключи на диске, в резервных копиях и снимках диска | ключ открытого аккаунта от процессов вашего пользователя |
| ключи от других пользователей машины | ключи от сеанса root |
| ключи после `awsv lock`, по окончании окна, после перезагрузки | ключ, который кто-то уже вывел, пока его аккаунт был открыт |
| аккаунт со своим паролем, пока вы работаете в другом | |

Поэтому держите аккаунт открытым ровно столько, сколько нужно:

```bash
awsv unlock 30m      # короткая работа: закроется сам через 30 минут
awsv unlock 8h       # рабочий день
awsv lock            # закончили раньше: закрыть всё сейчас
```

## Один пароль на всё или свой у каждого аккаунта

`awsv init` спрашивает, как вы хотите. Потом это можно поменять у любого
аккаунта.

| | один пароль (`shared`) | свой пароль у аккаунта (`own`) |
|---|---|---|
| что вводить утром | один пароль | пароль каждого нужного аккаунта |
| что открывает `awsv unlock work 30m` | все аккаунты на общем пароле | только `work` |
| что закрывает `awsv lock work` | все аккаунты на общем пароле | только `work` |
| ассистент или скрипт, работающий в одном аккаунте | может прочитать ключи всех | может прочитать ключ только открытого аккаунта |
| когда выбирать | аккаунты одинаково важны | один аккаунт важнее остальных, например production |

В одном сейфе уживаются оба варианта. Например, повседневные аккаунты на общем
пароле, а у `prod` свой:

```bash
awsv set prod --lock own        # шаг 1: общий пароль, шаг 2: новый пароль для prod
awsv unlock 8h                  # пароль аккаунта [default], на весь день
awsv unlock prod 30m            # только prod, на полчаса
awsv lock prod                  # закрыть prod; остальные остаются открытыми
awsv passwd prod                # сменить пароль только у prod
awsv set prod --lock shared     # вернуть prod на общий пароль
```

На шаге 1 gpg ничего не спросит, если общий пароль уже в памяти. Если
`set --lock` прервать или он упадёт на полпути, аккаунт откроется прежним
паролем, а если новый файл ключа уже на месте — новым. Без пароля, который его
открывает, аккаунт не останется.

Новому аккаунту можно сразу дать свой пароль:

```bash
awsv add prod --region eu-central-1 --lock own    # ввести ключ, затем дважды придумать пароль prod
awsv import client --lock own                     # то же для секции из ~/.aws/credentials
```

Чтобы каждый новый аккаунт получал свой пароль, выполните `awsv init --lock own`.
Аккаунты, которые уже есть в сейфе, сохранят свои. Отдельный новый аккаунт всё
равно можно добавить на общий пароль: `awsv add NAME --lock shared`.

### Нужно ли открывать каждый аккаунт?

Открывается каждый пароль, а не каждый аккаунт. Один `awsv unlock` открывает
все аккаунты на общем пароле; аккаунту со своим паролем нужен свой
`awsv unlock NAME`. Чтобы утром открыть всё сразу, выполните `awsv unlock all 8h`.
Команда спросит каждый пароль по одному разу: сначала общий, затем свои пароли
аккаунтов.

`aws` пароль никогда не спрашивает. Запертый аккаунт сразу отвечает ошибкой и
называет `awsv unlock NAME`; выполните её сами, и до конца окна работают и
`aws`, и задания cron, и скрипты, и ИИ-ассистенты.

В блоке каждого аккаунта `awsv status` показывает две строки. `lock` — каким
паролем открывается аккаунт. `state` — открыт ли он сейчас; там же точная
команда, которая его открывает или закрывает. Состояние общего пароля есть и в
блоке `VAULT`.

## Где что лежит

```
~/.local/share/awsv/
├── keys/             ключи, по зашифрованному файлу на аккаунт. Секреты — только здесь
│   ├── work.gpg
│   └── client.gpg
├── meta/             настройки аккаунта: регион, режим, пароль, номер аккаунта. Не секрет
│   ├── work
│   └── client
├── gnupg/            только для аккаунтов со своим паролем
│   └── client/       ключ GPG аккаунта client, его gpg-agent.conf и unlocked-until
├── active            одно слово: имя аккаунта [default]
├── lock              что получает новый аккаунт: shared или own
├── backup/           копии, сделанные перед каждым изменением
└── unlocked-until    когда кончается окно общего пароля; его читает awsv status
```

Вне этого каталога:

| Путь | Что это |
|---|---|
| `~/.gnupg/` | ключ GPG общего пароля |
| `~/.gnupg/gpg-agent.conf` | сколько общий пароль держится в памяти; задаёт `awsv unlock 30m` |
| `~/.aws/config` | awsv пишет блок между `# >>> awsv` и `# <<< awsv <<<`, остальное не трогает |
| `~/.aws/credentials` | пустой |
| `$XDG_RUNTIME_DIR/awsv/` | закэшированные часовые сессии, в памяти; выход из системы или перезагрузка их удаляет |
| `~/.local/share/bash-completion/completions/awsv` | автодополнение по Tab для bash, его кладёт `./install.sh` |

В каждом файле из `keys/` две строки, `AccessKeyId=…` и `SecretAccessKey=…`,
в зашифрованном виде. В блоке `~/.aws/config` — `[default]` и по секции
`[profile NAME]` на каждый аккаунт, и каждая из них вызывает `awsv creds NAME`.

У аккаунта со своим паролем свой каталог GPG, и gpg запускает для него
отдельный gpg-agent. Поэтому его пароль запоминается, забывается и отсчитывает
время отдельно от остальных.

## Что легко упустить

### Ключи не кладутся в `~/.aws/credentials`

Новый ключ попадает в сейф через `awsv add NAME`: команда читает его из терминала.
Если какая-то утилита сама записала ключ в `~/.aws/credentials`, перенесите его
командой `awsv import SECTION`. Пока ключ там, `awsv status` показывает красный
`WARNING`.

### Пустой `~/.aws/credentials` — это правильно

Ключи лежат в `keys/`, а AWS CLI получает их через `~/.aws/config`. Пустой файл
можно не удалять, он ничему не мешает.

### Ключ, оставшийся в `~/.aws/credentials`, главнее сейфа

AWS CLI сначала читает `~/.aws/credentials`, и к awsv обращается, только если
для профиля в файле ничего нет. Забытый там ключ будет использоваться вместо
сейфа, и ничто об этом не предупредит. Проверить можно командой
`aws configure list`: в строке `access_key` должно стоять `custom-process`.

### Удаление аккаунта не отзывает ключ

`awsv rm NAME` удаляет зашифрованный файл и профиль, но в AWS ключ продолжает
работать. Если он больше не нужен, деактивируйте его в IAM. То же касается
старого ключа после `awsv rekey NAME`.

### Режим session или direct

У каждого аккаунта есть режим. Его видно в `awsv ls`, а меняется он командой
`awsv set NAME --mode direct` или `--mode session`.

| | session (по умолчанию) | direct |
|---|---|---|
| что получает программа | часовую сессию, ключ начинается с `ASIA` | сам ключ, начинается с `AKIA` |
| если утёк | перестаёт работать в течение часа | работает, пока не отзовут в IAM |
| вызовы IAM API | запрещены: сессия без MFA их делать не может | работают |
| прогон дольше часа | сессия обновится сама, но в этот момент аккаунт должен быть открыт | не влияет |

Для аккаунта, с которым работает Terraform, ставьте `direct`: Terraform часто
меняет роли и политики IAM, а прогоны бывают долгими. Для ручной работы
подходит `session`.

### Долгий прогон Terraform в режиме session

Когда сессия истекает, SDK AWS снова вызывает awsv и получает новую. Для этого
аккаунт должен быть открыт. Пароль держится в памяти столько, сколько вы
выбрали, считая от момента ввода, — пользуетесь вы им или нет. Прогон длиннее
окна упадёт посередине. Перед долгим прогоном либо переведите аккаунт в
`direct`, либо откройте его с запасом: `awsv unlock NAME 8h`.

### Когда спрашивается пароль

Только когда вы сами запускаете `awsv unlock`, `awsv show NAME` или
`awsv set NAME --lock own`. `aws` и всё, что работает через него, пароль не
спрашивают. awsv вызывает gpg с `--pinentry-mode error`, и запертый аккаунт
сразу отвечает ошибкой. Иначе gpg открыл бы окно пароля на терминале из
`GPG_TTY`, где отвечать может быть некому. Пароль остаётся открытым на окно, выбранное
в `awsv unlock`. У каждого своего пароля окно своё.

Команде без терминала спросить негде, и она падает с
`Error when retrieving credentials from custom-process`. Так бывает у заданий
cron, у скриптов и у ИИ-ассистентов. В ошибке указано имя аккаунта. Выполните с
этим именем `awsv unlock NAME` в своём терминале, и они снова заработают.

### После перезагрузки

Делать ничего не нужно. Все аккаунты стартуют запертыми, кэш сессий пуст.
Первая команда `aws` в терминале спросит пароль.

### Как посмотреть сохранённый ключ

```bash
awsv show work
```

Команда выводит идентификатор ключа и секрет. Работает она только в настоящем
терминале: в трубе, в скрипте или в оболочке ассистента откажет, чтобы секрет не
попал в журнал. То же самое без awsv:

```bash
gpg --decrypt ~/.local/share/awsv/keys/work.gpg                                     # общий пароль
gpg --homedir ~/.local/share/awsv/gnupg/work --decrypt ~/.local/share/awsv/keys/work.gpg   # свой пароль
```

Никогда не просите ИИ-ассистента выполнить ни одну из этих команд. Всё, что он
запускает, остаётся в истории его сессии на диске, и ключ пришлось бы отзывать.

### Как сменить пароль

```bash
awsv passwd              # общий пароль
awsv passwd client        # пароль, которым открывается client: свой или общий
```

Команда спросит текущий пароль, затем дважды новый. Файлы в `keys/` при этом не
меняются: пароль запирает ключ GPG, а не каждый файл по отдельности.

### Если пароль забыт

Без пароля аккаунт не открыть. Выход — новый ключ из IAM для каждого аккаунта,
который этот пароль открывал.

Общий пароль:

```bash
awsv rm work --yes                                     # для каждого аккаунта на общем пароле; пароль не нужен
gpg --delete-secret-and-public-keys "awsv local vault"  # старый ключ GPG
awsv init                                              # новый ключ GPG и новый пароль
awsv add work --region eu-central-1                    # с новым ключом из IAM
```

Свой пароль одного аккаунта; остальные аккаунты это не затрагивает:

```bash
awsv rm client --yes                                   # удалит и его ключ GPG
awsv add client --region us-east-2 --lock own          # новый ключ из IAM, новый пароль
```

Затем деактивируйте старые ключи в IAM. Поэтому резервная копия ключа GPG и не
нужна: восстановление — это выпуск нового ключа в IAM.

### Сколько может быть аккаунтов

Число аккаунтов не ограничено. Каждый хранится отдельным файлом в `keys/`.

### У каждого пользователя свой сейф

Всё лежит в домашнем каталоге того, кто запускает awsv. У двух пользователей на
одной машине два сейфа, два пароля и два своих `[default]`. Не запускайте awsv
через `sudo`: `sudo` может подменить `HOME`, и awsv возьмёт чужие файлы.

ИИ-ассистент пользуется сейфом того пользователя, под которым запущен. Если он
работает под root, а вы — под собой, ваш сейф ему недоступен.

### В каталоге backup лежат прежние ключи

Перед тем как изменить `~/.aws/credentials`, каждый `import` сохраняет копию
файла в `backup/credentials.<время>.gpg`. Копия зашифрована, но ключи в ней те
же. Когда перенос закончен и всё работает, эти файлы можно удалить.

## Когда что-то идёт не так

| Что видно | Почему | Что делать |
|---|---|---|
| `Error when retrieving credentials from custom-process: awsv: cannot open 'NAME'` | аккаунт заперт, а у команды не было терминала | `awsv unlock NAME` в своём терминале |
| `awsv unlock work` открыл и другие аккаунты | все они на общем пароле | дать аккаунту свой: `awsv set NAME --lock own` |
| `every account has its own passphrase — name one` | `awsv passwd` без имени, а общего пароля нет | `awsv passwd NAME` |
| `lock is 'shared' or 'own'` | опечатка после `--lock` | `--lock own` или `--lock shared` |
| `STS refused a session for 'NAME'` | AWS не принимает сохранённый ключ | проверить ключ в IAM; `awsv rekey NAME` |
| `AccessDenied` на вызовах IAM, чаще от Terraform | аккаунт в режиме session | `awsv set NAME --mode direct` |
| красный `WARNING` в `awsv status` | ключ остался в `~/.aws/credentials` | `awsv import SECTION` |
| `aws configure list` показывает `shared-credentials-file` | ключ остался в `~/.aws/credentials`, и он главнее сейфа | `awsv import SECTION` |
| `~/.aws/config already defines [default] outside the awsv block` | в конфиге есть свой `[default]` | `awsv init --take-default` |
| `show prints a secret, so it runs only in a terminal` | `show` запущена в трубе или скрипте | запустить в своём терминале |
| `no session cache` от `./install.sh` | не задана `XDG_RUNTIME_DIR` | ничего: каждый вызов пойдёт в STS, чуть медленнее |

## Тесты

```bash
./tests/test_awsv.sh             # сами команды
./tests/test_docs_commands.sh    # каждая команда, которую показывают справка и документация
./tests/test_awsv_sso.sh         # awsv-sso, с подменой aws: в AWS ничего не уходит
```

Второй тест собирает каждое `awsv …` из справки, обоих README, страниц в
`docs/`, вывода `status` и сообщений awsv и запускает его. Текст, который
выглядит как команда, но ею не является, тест не пропустит.

Тесты работают во временном домашнем каталоге с поддельными ключами. Ваш сейф,
`~/.aws` и gpg-agent они не трогают. Одна проверка обращается к AWS STS с
поддельным ключом; `AWSV_TEST_NETWORK=0` её пропускает. Удачный прогон
заканчивается строкой `0 failed`.
